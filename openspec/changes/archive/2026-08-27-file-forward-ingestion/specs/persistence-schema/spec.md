## MODIFIED Requirements

### Requirement: Deep-link intents persist as opaque owner-bound records

The schema SHALL contain a `telegram.interaction_intents` table holding opaque deep-link intent records: an app-minted UUID primary key with no default, the bot identifier, the owning Telegram user and originating chat, an intent-kind vocabulary constrained by CHECK to `operation_status`, the referenced Platform operation, the source address the intent presents - nullable, because attachment captures present a blob rather than an address - and creation and expiry timestamps. The table SHALL also carry a bounded JSON metadata column reserved for capture provenance facts (forward origin, or the stored blob reference and media facts of an attachment); the stored address SHALL be null exactly when metadata carries a blob reference. No credential and no message content SHALL be stored in either place.

#### Scenario: A fresh database has the intents table

- **WHEN** the schema file is applied to an empty database
- **THEN** `telegram.interaction_intents` exists with its UUID key, kind vocabulary, ownership columns, nullable source address, bounded object-typed metadata, and timestamps

#### Scenario: Intent identifiers are minted, never generated by the database

- **WHEN** an intent row is inserted without supplying an id
- **THEN** the insert fails, because the identifier is the opaque token clients see and the application mints it

#### Scenario: An attachment intent persists its blob facts instead of an address

- **WHEN** an attachment capture's intent row is inserted with a null source address and metadata naming the stored blob reference
- **THEN** the insert succeeds, a URL-carrying insert still succeeds as before, and a row with neither an address nor blob metadata is refused by the table's own constraint
