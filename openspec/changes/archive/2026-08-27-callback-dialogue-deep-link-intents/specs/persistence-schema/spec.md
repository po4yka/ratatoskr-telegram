## MODIFIED Requirements

### Requirement: Deep-link intents persist as opaque owner-bound records

The schema SHALL contain shared interaction-token records for deep-link operation intents. Each record SHALL hold an app-minted high-entropy opaque token with no database default; the `deep_link` surface; bot, owning Telegram user and originating chat scope; the closed operation-intent action; referenced Platform operation; bounded object-typed capture presentation payload; creation and expiry timestamps; and one-time consumption evidence. The stored payload SHALL present either a source address or stored blob facts and MAY carry bounded forward provenance. No credential, raw message content, or client-interpretable business state SHALL be stored in the token itself.

#### Scenario: A fresh database has the intents table

- **WHEN** the schema file is applied to an empty database
- **THEN** interaction-token storage can represent a deep-link operation intent with its action, operation reference, owner scope, bounded payload, expiry, and consumption evidence

#### Scenario: Intent identifiers are minted, never generated by the database

- **WHEN** a deep-link intent row is inserted without supplying a token
- **THEN** the insert fails because the application must mint the opaque value clients receive

#### Scenario: An attachment intent persists its blob facts instead of an address

- **WHEN** an attachment capture's deep-link intent stores no source address and its bounded payload names the stored blob reference
- **THEN** the insert succeeds, a URL-carrying intent still succeeds, and a record presenting neither an address nor blob facts is refused

### Requirement: Callback confirmations persist in generalized dialogue and token state

The current first-version schema SHALL persist generalized dialogue records and interaction tokens instead of repository-specific callback-flow tables. A dialogue SHALL carry its kind, bot, owning Telegram user, originating chat, expected message, bounded typed state payload, current step/version, lifecycle state, expiry, and timestamps. Each app-minted callback token SHALL reference one expected dialogue version and action, carry complete scope and expiry, and record one-time consumption. A transaction consuming a token SHALL lock and advance the expected dialogue version so concurrent confirm/cancel/replay attempts have one winner. No credential, raw provider response, private message body, or free-form mutable policy JSON SHALL be stored.

#### Scenario: A fresh database enforces generalized dialogue and token authority

- **WHEN** the root schema file is applied to an empty database
- **THEN** dialogue and interaction-token storage exists with application-minted opaque keys, owner/chat/message bindings, closed surface/action/lifecycle vocabularies, expiry, version, and consumption evidence

#### Scenario: Concurrent terminal decisions have one winner

- **WHEN** confirm and cancel tokens for the same expected dialogue version are consumed concurrently
- **THEN** one transition advances the dialogue and the other changes no state

#### Scenario: The schema stores references instead of secrets

- **WHEN** a repository confirmation dialogue is inspected
- **THEN** it contains only bounded stable target and action references needed for execution and no GitHub token, Platform session credential, raw callback payload, or private message body

### Requirement: Stale interaction state can be cleaned in bounded batches

The schema and persistence boundary SHALL support a bounded, idempotent cleanup transaction that expires active dialogues at their deadline and removes eligible expired or consumed tokens and retention-expired terminal dialogues. The cleanup SHALL never cross the `telegram` schema or cascade into operations, message bindings, updates, or outbound jobs.

#### Scenario: Cleanup touches only eligible interaction state

- **WHEN** a cleanup batch runs with stale and live tokens/dialogues plus linked operation and message-binding rows
- **THEN** only eligible interaction rows expire or disappear and every live token, operation, binding, update, and outbound job remains unchanged
