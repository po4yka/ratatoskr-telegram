## ADDED Requirements

### Requirement: Deep-link intents persist as opaque owner-bound records

The schema SHALL contain a `telegram.interaction_intents` table holding opaque deep-link intent records: an app-minted UUID primary key with no default, the bot identifier, the owning Telegram user and originating chat, an intent-kind vocabulary constrained by CHECK to `operation_status`, the referenced Platform operation, the source address the intent presents, and creation and expiry timestamps. No credential and no content beyond the submitted address reference SHALL be stored.

#### Scenario: A fresh database has the intents table

- **WHEN** the schema file is applied to an empty database
- **THEN** `telegram.interaction_intents` exists with its UUID key, kind vocabulary, ownership columns, and timestamps

#### Scenario: Intent identifiers are minted, never generated by the database

- **WHEN** an intent row is inserted without supplying an id
- **THEN** the insert fails, because the identifier is the opaque token clients see and the application mints it

### Requirement: Outbound payloads are stored whole

The `telegram.outbound_jobs` table SHALL store each job's message payload so that text, parse mode, and inline keyboard survive restarts and retries bit-identically, alongside the existing content hash that deduplicates identical re-renders.

#### Scenario: A queued job restores its full payload after restart

- **WHEN** a claimed-but-undelivered job with markup is reclaimed after a simulated crash
- **THEN** the redelivered request carries the same text, parse mode, and buttons it was enqueued with
